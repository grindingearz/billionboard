# BillionBoard — Environment Variable Setup

This project runs in three places:

| Environment | Platform | Config source |
|-------------|----------|---------------|
| Local dev | Your Mac | `.env.local` |
| Frontend / API routes | Vercel | Vercel dashboard → Settings → Environment Variables |
| Background jobs / Postgres | Railway | Railway dashboard → Service Variables |

---

## 1. Local development

```bash
cp .env.example .env.local
```

Open `.env.local` and fill in real values. At minimum you need:

```
DATABASE_URL=postgresql://user:pass@localhost:5432/billionboard
SESSION_SECRET=<any long random string>
ADMIN_PASSWORD=<pick a strong password>
NEXT_PUBLIC_APP_URL=http://localhost:3000
NEXT_PUBLIC_PROJECT_NAME=BillionBoard
NEXT_PUBLIC_TOKEN_TICKER=BOARD
NEXT_PUBLIC_SOLANA_NETWORK=mainnet-beta
```

Generate a secure `SESSION_SECRET` in your terminal:

```bash
openssl rand -hex 32
```

Do the same for `CRON_SECRET`.

After changing env vars, restart the dev server:

```bash
npm run dev
```

> Next.js only reads `.env.local` at startup — changes are not hot-reloaded.

After adding variables in Vercel, redeploy the project for changes to take effect:

```bash
vercel --prod
# or trigger a new deployment from the Vercel dashboard
```

> **Rule:** If a variable name starts with `NEXT_PUBLIC_`, its value is embedded in the client-side JavaScript bundle and visible to anyone who visits the site. Never put database URLs, API secrets, private keys, or R2 credentials in a `NEXT_PUBLIC_` variable.

## 3. Railway variables

Railway hosts the PostgreSQL database and any background job workers (daily billing cron, holder snapshot indexer).

### PostgreSQL

Railway auto-generates `DATABASE_URL` when you provision a Postgres service. Copy that value into:
- Your `.env.local` (for local dev pointing at Railway Postgres, or use a local Postgres instead)
- Vercel environment variables under `DATABASE_URL`

### Background job worker service variables

In your Railway worker service, set these variables:

| Variable | Notes |
|----------|-------|
| `DATABASE_URL` | Auto-generated by Railway Postgres — reference it with `${{Postgres.DATABASE_URL}}` |
| `HELIUS_API_KEY` | Same value as Vercel |
| `HELIUS_RPC_URL` | Same value as Vercel |
| `FEE_CREATOR_WALLET` | Same value as Vercel |
| `AD_REVENUE_WALLET` | Same value as Vercel |
| `MANAGEMENT_WALLET` | Same value as Vercel |
| `DISTRIBUTION_WALLET` | Same value as Vercel |
| `TREASURY_WALLET` | Same value as Vercel |
| `R2_ACCOUNT_ID` | Same value as Vercel |
| `R2_ACCESS_KEY_ID` | Same value as Vercel |
| `R2_SECRET_ACCESS_KEY` | Same value as Vercel |
| `R2_BUCKET_NAME` | Same value as Vercel |
| `R2_PUBLIC_URL` | Same value as Vercel |
| `CRON_SECRET` | Same value as Vercel — used to authenticate billing trigger calls |

> Background jobs run in Node.js on Railway, not in a browser. They must not rely on `NEXT_PUBLIC_` values — those are only substituted at Next.js build time and are not available to standalone worker scripts.

## 4. Security warnings

**Do not commit secrets.** The following files are blocked in `.gitignore` and must never be committed:

```
.env
.env.local
.env.development
.env.production
```

**Specific variables that must never be public:**

| Variable | Risk if leaked |
|----------|---------------|
| `DATABASE_URL` | Full read/write access to all user data |
| `PRIVY_APP_SECRET` | Can impersonate any user in your Privy project |
| `R2_SECRET_ACCESS_KEY` | Full access to your image storage bucket |
| `SESSION_SECRET` | Can forge session cookies and impersonate any user |
| `DISTRIBUTION_WALLET_PRIVATE_KEY` | Controls the wallet that holds USDC payout funds |
| `ADMIN_PASSWORD` | Grants access to the admin dashboard |
| `CRON_SECRET` | Can trigger billing runs and drain advertiser balances |

**Wallet key hygiene:**

- The `DISTRIBUTION_WALLET` is a hot wallet used only for outbound USDC claim payouts. Fund it with just enough USDC to cover expected claims — never park the treasury here.
- Keep `TREASURY_WALLET` and `MANAGEMENT_WALLET` as hardware wallets or multi-sig. Do not put their private keys in the app at all.
- Rotate `SESSION_SECRET` and `CRON_SECRET` immediately if you suspect they have been exposed (existing sessions will be invalidated — users will need to log in again).

## 5. Runtime validation

The file `lib/env.ts` exports a validated `env` object. In production it throws a descriptive error at startup if any critical variable is missing, so you catch misconfiguration at deploy time rather than at request time.

```ts
import { env } from '@/lib/env'

// Example usage in a server route or server component:
const db = env.databaseUrl    // throws in production if DATABASE_URL is missing
const mint = env.boardMint    // null until token launches — check before using
```

**Do not import `lib/env.ts` from client components.** Client components should read `NEXT_PUBLIC_` variables directly from `process.env`:

```ts
// In a client component — fine
const appUrl = process.env.NEXT_PUBLIC_APP_URL

// In a client component — DO NOT do this
import { env } from '@/lib/env'  // leaks server-only values into the bundle
```
